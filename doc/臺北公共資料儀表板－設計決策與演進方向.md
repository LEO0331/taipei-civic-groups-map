# 臺北公共資料儀表板

## 設計決策、使用情境與演進方向

**文件定位：** 以公開資料為基礎的查詢、比較與資料品質檢視說明  
**系統型態：** Vite、React、TypeScript 靜態網站；資料轉換後以 JSON 載入  
**更新日期：** 2026 年 7 月

> **核心結論**：此儀表板的價值不在替使用者作出醫療、資格、營運或品質判斷，而在於把分散的政府公開名單轉成可搜尋、可比較、可追溯的資料入口，讓後續確認工作有更清楚的起點。

## 一、它協助的是什麼決策？

儀表板將不同主題的公開名單、服務據點與行政資料，以一致的摘要卡、分布圖、目錄、資料品質與來源說明呈現。它適合支援「初步盤點」與「下一步查證」的決策，而非直接代替現場確認或專業判斷。

| 使用者／情境 | 可獲得的判斷支援 | 應保留的確認步驟 |
| --- | --- | --- |
| 一般市民 | 依行政區、聯絡資訊與官方欄位縮小查找範圍，建立可聯絡的候選清單。 | 向機構或主管機關確認即時營業、資格、名額、費用與服務內容。 |
| 社區工作者與公共服務人員 | 看見特定行政區的服務據點分布，用於外展、轉介前資訊整理與資源盤點。 | 不得把名單當成轉介品質、可收案狀態或服務能力的保證。 |
| 研究、媒體與非營利組織 | 以固定資料快照比較區域分布、欄位完整度與資料更新狀態。 | 回到來源資料與更新日期，避免將橫斷面資料解讀為趨勢或因果。 |
| 資料維護者 | 從缺值、重複、未知行政區與轉換報告找出應優先回查的資料問題。 | 在重新發布前，回看原始檔與官方說明，確認欄位語意沒有改變。 |

## 二、適合與不適合的使用場景

### 適合

- **服務據點或公共名單的跨區查找：** 先以區域與文字搜尋找到可能的機構，再用電話、來源頁或外部地圖查詢完成確認。
- **資料盤點與行政區比較：** 以摘要卡和分布圖查看不同區域的紀錄數、電話完整度與資料覆蓋情況。
- **公開資料品質檢核：** 在資料更新後，檢查重複列、缺少關鍵欄位、格式異常與未知行政區。
- **靜態展示或離線閱讀：** 資料轉為可快取的 JSON，適合在低維運成本的靜態網站或 PWA 環境提供查詢。

### 不適合

- 緊急醫療、即時預約、床位、疫苗、供餐或營業狀態查詢。
- 判定服務資格、收案資格、招生名額、品質、安全、醫療能力或機構推薦。
- 以地址推定機構精確位置，或以名單存在與否推論機構目前仍在營運。
- 將單一公開名單延伸為企業排名、能源績效、碳排、投資或法規遵循判斷。

## 三、資料到畫面的設計路徑

系統採取「先轉換、後展示」的資料路徑。公開來源不在使用者開啟頁面時直接解析，而是先經由專案腳本下載或讀取人工放置的原始 CSV，轉換成紀錄檔、摘要檔與轉換報告，再交由 React 模組呈現。

```text
臺北市公開資料來源
  → 原始 CSV／下載檔
  → 編碼偵測與欄位轉換
  → records.json、summary.json、conversion-report.json
  → 儀表板卡片、圖表、篩選名冊與資料註記
  → PWA 快取
```

| 設計選擇 | 採用原因 | 代價與控制方式 |
| --- | --- | --- |
| 靜態 JSON 資料快照 | 可部署於靜態主機、減少瀏覽時對上游來源的依賴、資料轉換可重現。 | 非即時資料；以資料來源、更新日期與免責說明提醒使用者回查。 |
| 保留原始值與衍生值 | 原始欄位便於追溯；正規化欄位支援一致搜尋、去重與分群。 | 欄位較多；將衍生規則集中於轉換腳本並輸出品質報告。 |
| 摘要與目錄共用篩選結果 | 卡片、圖表、表格與匯出都由同一份 `filteredRecords` 推導。 | 前端需自行聚合；以 memoization、分頁與聚合圖表控制成本。 |
| 外部地圖查詢連結 | 地址資料仍可協助使用者查找，同時避免未確認座標被呈現為精確標記。 | 需跳轉外部服務；只有官方確認座標才顯示標記。 |

## 四、資料轉換與品質控制

### 欄位與編碼為何先保守處理？

不同資料集的 CSV 編碼與欄位型別不一致。轉換流程支援 UTF-8-SIG、Big5 與 CP950，並先將電話、郵遞區號、行政區代碼與來源序號讀成字串，再做正規化。這可保留前導零、避免電話被轉為數值或科學記號，也讓資料列在來源與畫面間保有可追溯性。

### 為何不採取「越多修正越好」的清理方式？

公開資料的拼字、地址與名稱差異不一定代表錯誤。去重策略以來源 ID 優先，或以名稱、地址、電話等正規化組合判斷「明確重複」；疑似相近但無法確定的資料保留，並讓轉換報告揭露。這避免把不同據點錯合併，也承認資料清理不是無成本的推論。

| 問題 | 目前做法 | 理由／可觀察訊號 |
| --- | --- | --- |
| 多種 CSV 編碼 | 依序嘗試 UTF-8-SIG、Big5、CP950。 | 臺灣公開資料常混用編碼；轉換失敗會在流程中明確暴露。 |
| 前導零與電話格式 | 全欄先讀字串，另產生正規化欄位。 | 避免資料型別破壞；保留顯示用原值與搜尋用值。 |
| 行政區不一致 | 先使用官方代碼，無代碼時才從地址保守辨識。 | 代碼優先可減少文字解析誤判；未知值列入品質報告。 |
| 地址但沒有官方座標 | 不自動地理編碼，也不建立精確地圖標記。 | 避免錯位與不當精確性；改提供外部地圖查詢。 |
| 來源欄位缺漏或改名 | 轉換報告統計缺值、重複、異常格式與未辨識欄位。 | 讓資料更新失敗或品質下降可被偵測，而不是靜默發布。 |

## 五、篩選與搜尋為何這樣設計？

篩選採「先縮小範圍、再找文字」的順序：行政區等高辨識度欄位放在下拉篩選；是否有電話、設立別、資料類型等狀態放在次要篩選；名稱、地址、電話與代碼則納入單一搜尋框。這種設計同時照顧知道目標區域的使用者與只記得部分名稱或地址的人。

| 設計原則 | 實作方式 | 帶來的效果 |
| --- | --- | --- |
| 一份篩選結果 | 所有視圖從同一個 `filteredRecords` 產生。 | 摘要卡、圖表、目錄與匯出數字一致，減少跨視圖誤解。 |
| 可預期的分面篩選 | 使用有限集合的行政區、類型或布林狀態。 | 使用者可快速知道可選範圍，也不必記住原始欄位格式。 |
| 容錯文字搜尋 | 比對正規化後的名稱、區域、地址、電話、代碼等欄位。 | 可處理全形／半形、空白與電話格式的常見差異。 |
| 分頁與重設頁碼 | 過濾條件變動時回到第一頁，表格只渲染當頁列。 | 避免條件變動後出現空白頁，並控制大量列的 DOM 成本。 |
| 不保存敏感查詢 | 篩選狀態僅在前端使用，不建立個人化追蹤。 | 降低健康、社福等主題的隱私風險；代價是無跨裝置續用。 |

> **篩選的取捨**：目前的前端篩選在單一資料集為中小型公開名單時，可提供直接、低延遲、無伺服器維運的體驗；但它不適合作為所有資料規模下的固定答案。資料量、更新頻率與跨資料集查詢需求增加後，查詢責任應往後端或邊緣層移動。

## 六、大型資料與效能：目前方法、邊界與替代方案

目前架構在載入資料後，以記憶化計算處理篩選與彙總，目錄採分頁呈現，圖表只繪製聚合後的分類數字而非每筆原始列。這降低了重複運算、DOM 節點數與圖表負擔，也符合多數公開名單以數百至數千筆為主的使用情境。

| 需求條件 | 適合方案 | 主要代價／注意事項 |
| --- | --- | --- |
| 中小型、更新較少、靜態部署 | 前端載入 JSON + `useMemo` 篩選 + 分頁。 | 初次下載與 JSON 解析仍在瀏覽器完成；多模組累積時需管理資產體積。 |
| 數萬筆以上或低階裝置卡頓 | 虛擬化表格、Web Worker 搜尋／聚合、按模組延遲載入。 | 實作與除錯複雜度提高；需處理 worker 通訊與可及性。 |
| 頻繁更新、多人同時查詢 | 後端／邊緣 API 的條件查詢、索引與游標分頁。 | 需要 API 維運、快取、速率限制、資安與監控，也要設計查詢契約。 |
| 跨資料集關聯或歷史分析 | 資料庫、預先彙總表、版本快照與可重現的 ETL。 | 資料模型與更新治理成本較高；應先確認真正的分析需求。 |

### 何時該從前端篩選改成後端查詢？

- 單一模組的下載大小、初次可互動時間或記憶體使用已影響低階裝置。
- 使用者需要深層條件、排序、跨資料集關聯，或要存取大量歷史版本。
- 資料更新頻率提高，且靜態重新建置與 PWA 快取更新已無法滿足資料新鮮度。
- 需要權限、使用量監控、速率限制或稽核紀錄，不能再由純靜態檔案承擔。

若轉向後端，較合適的起點是以白名單欄位建立查詢參數，提供游標分頁、伺服端彙總與快取標頭，而不是把任意 SQL 或整份資料庫暴露給前端。前端仍可保留既有的篩選語意，改由 API 回傳當頁資料與同口徑摘要。

## 七、地圖、健康與公共服務資料的安全邊界

資料集涵蓋醫療、社福、兒少、動物服務、產業與其他公共主題。這些名單容易被誤讀成即時能力、資格證明或品質排名，因此每個模組都需要以資料來源與免責說明界定範圍。健康與社福相關頁面尤其避免提供診斷、治療、營養、接種、資格或收案建議。

| 風險 | 採用的邊界 | 原因 |
| --- | --- | --- |
| 精確位置誤導 | 只有來源已確認官方座標的資料才顯示標記；地址型資料僅提供外部查詢連結。 | 地理編碼可能錯位，且「看似精確」比沒有標記更容易造成誤用。 |
| 即時性誤解 | 以公開名單／資料快照呈現，明示須向據點與主管機關確認。 | 名單無法證明目前營業、名額、庫存、預約或收案狀態。 |
| 品質與推薦推論 | 不做排名、推薦、醫療品質、環境或法遵推論。 | 資料欄位通常不足以支撐這些結論，推論可能造成實質傷害。 |
| 兒少與敏感服務 | 避免處理住址、個資與未經驗證的精確座標；維持最小必要呈現。 | 公開可查不等於適合聚合、標記或進一步擴散。 |

## 八、已知限制與可持續改善方向

| 面向 | 目前限制 | 下一步改善 |
| --- | --- | --- |
| 模組導航 | 資料集增加後，手動匯入與導航設定容易分散。 | 建立資料集註冊表，集中定義模組、來源、路由、快取與顯示能力。 |
| 前端載入 | 模組愈多，打包體積與首次載入壓力上升。 | 以路由層級動態載入，依主題拆分 chunk，量測首次可互動時間。 |
| 資料新鮮度 | 靜態快照不具即時性，PWA 還可能保留舊版檔案。 | 在轉換流程寫入版本與更新時間；採內容雜湊或明確快取版本策略。 |
| 資料語意 | 相同欄位名稱在不同來源可能代表不同概念。 | 將欄位字典、來源備註與轉換假設納入資料註記，更新前做 schema 驗證。 |
| 可及性與實用性 | 資料正確不代表每位使用者都能順利理解或操作。 | 增加鍵盤操作、表格語意、色彩對比檢查與任務式使用者測試。 |
| 分析深度 | 目前偏向探索與盤點，非長期趨勢或因果分析。 | 若有穩定歷史版本，再建立時間序列、差異報告與可下載方法說明。 |

### 建議追蹤的決策指標

- **資料層：** 轉換成功率、欄位缺值率、重複率、未知行政區率、資料距最後更新的時間。
- **體驗層：** 各模組 JSON 大小、首次可互動時間、搜尋延遲、分頁切換延遲、低階裝置記憶體使用。
- **治理層：** 來源連結是否可用、欄位 schema 是否變動、免責說明是否覆蓋敏感主題、PWA 快取版本是否同步。

## 九、結語

這個儀表板以「讓公開資料更容易被理解與核對」為目標：先把來源資料標準化、揭露其品質與限制，再用一致的篩選、摘要與目錄降低查找成本。靜態前端架構在目前資料規模下提供了低維運、可重現與適合 PWA 的平衡；同時保留清楚的轉換門檻，讓系統在資料量、更新頻率或查詢複雜度提高時，可以有紀律地演進為更適合的後端查詢架構。

> **使用原則**：把儀表板視為公開資料的探索與查證入口，而非即時服務承諾、專業建議或機構評比工具。任何與健康、資格、營運、費用、可用性或安全有關的實際決定，均應回到個別機構與主管機關取得最新確認。
